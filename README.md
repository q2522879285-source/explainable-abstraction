# Explainable Abstraction

把抽象的模型输出、架构、策略或工作思路，变成别人能看懂、能检查、能开始使用的交付物。

> **抽象结构 → 人话解释 → 可检查结构 → 可执行产物 → 结果回读**

这是一份跨领域 Skill：它负责理解与落地之间的转换，不替代影视、数据、代码、网页或其他领域 Skill。

## 适合什么时候用

- 需要把复杂结论讲给非专业读者
- 需要让方案可以被复核、接手或执行
- 需要把同一机制转成说明文、流程图、原型、脚本或解释视频
- 需要保留约束、证据、假设和不确定性，而不是只要一句漂亮口号

不适用于纯翻译、只做摘要、固定格式转换或只要正式定义的任务。

## 最小输入

```text
目标：希望读者理解什么、做什么
对象：正在解释的结论、架构、策略或工作思路
约束：必须保留的事实、边界、证据、格式和资源
受众：谁会阅读或使用结果
```

缺少非关键输入时可以先做合理假设，并把假设标出来；会改变路线的输入应先确认。

## 标准输出

1. **人话解释**：一句结论 + 机制的短说明。
2. **可检查结构**：对象、关系、约束、证据、假设、输出和停止条件。
3. **可执行产物**：选择最小合适媒介，给出可以直接开始的文件、步骤、样例或脚本。
4. **回读验收**：说明如何确认解释没有改写原意、产物可打开/运行/检查，以及下一步动作。

推荐的交付骨架：

```text
结论与影响
机制（抽象词 → 可观察现象 → 下一步动作）
可检查结构
可执行产物
验收与下一步
```

## 媒介选择

| 问题形态 | 优先媒介 |
| --- | --- |
| 线性判断、规则 | 短句和说明文 |
| 关系、流程、层级 | 图、表、流程图 |
| 分支多、需要探索 | 交互网页或原型 |
| 时间、空间、动作 | 解释视频或分镜 |
| 需要证明行为 | 脚本、样例或可执行演示 |

先交付“结论 + 一种最小辅助表示”，不要为了完整而同时制作所有媒介。

## 最小示例

输入：

```text
目标：让新同事理解一次发布为什么要分阶段
对象：发布流程说明
约束：不能跳过回滚方案；每一步都要有负责人
受众：第一次接手发布的新同事
```

输出应能定位到：

- 人话：先小范围验证，再扩大范围；每一阶段都保留回退路径。
- 结构：阶段 → 入口条件 → 负责人 → 观测信号 → 退出/回滚条件。
- 产物：一张流程图 + 一份可复制的发布清单。
- 验收：新同事能按图找到下一步，并说出何时停止或回滚。

更多格式化示例见 [`examples/minimal.md`](examples/minimal.md)。

## 安装

### Codex / Claude Code

把仓库目录复制到对应的 `skills/` 目录，并保留 `SKILL.md` 与 `agents/openai.yaml`：

```text
<skills-root>/explainable-abstraction/SKILL.md
<skills-root>/explainable-abstraction/agents/openai.yaml
```

在任务中调用：

```text
Use $explainable-abstraction to turn this abstract result into a human-readable, checkable, and actionable deliverable.
```

### 直接复用

不使用 Skill 系统时，直接把 [`SKILL.md`](SKILL.md) 作为工作约定提供给模型即可。

## 边界

- 不自动生成网页、视频或其他外部资产；只有用户要求或媒介确实能解决理解问题时才制作。
- 领域事实、计算、代码、影视、数据和外部平台操作仍由相应领域方法负责。
- “方便理解”不等于删除约束、证据、假设或不确定性。
